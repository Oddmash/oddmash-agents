# Rollout

1. Create the private `Oddmash/oddmash-agents` repository. Keep reusable concepts and product skills in `oddmash-skills`, not in the runtime.
2. Run offline tests and check the GitHub API and model integration against one public Oddmash UI PR in report-only mode. Compare findings with maintainer review; track accepted findings, dismissed findings, latency, cost and coverage omissions.
3. After explicit approval, register a dedicated GitHub App for selected public repositories only. Permissions: metadata read, contents read, checks read, pull requests read/write for advisory comments. No administration, actions write, secrets, deployment or branch write permission. Keep installation credentials outside the repo.
4. Integrate trusted, pinned execution with a per-PR concurrency group. For automation, trigger on PR changes and check completion without ever executing the PR's code in a privileged context. Check head SHA again before posting; add cross-run finding-level deduplication and stale-comment handling before expanding the pilot.
5. Add Maintainer, Design Auditor and Release Manager as separate advisory modules only after reviewer precision and cost are documented. Developer automation is a separate approval-gated project.

The organization workflow supports targeted PR event dispatch from trusted repository relays and a ten-minute fallback scan until `REVIEWER_EVENT_MODE=true`. Formal approval requires zero validated findings, no omitted files, and complete passing current check evidence. High-confidence actionable defects receive a review comment and maintainer follow-up. Uncertain or incomplete coverage receives a single advisory after final checks. Later advisory outcomes for the same head update that review. Human code-owner review and merge remain separate. The central webhook reviews explicitly approved private repositories with stricter data filtering. Approved private repositories may use the separate gated merge policy only for low-risk eligible changes; all existing protection and evidence requirements remain.

Current limits: CLI, manually dispatched Actions, and opt-in scheduled App polling; central webhook, first 100 files with strict review budgets, base guidance capped at 24,000 characters, no skill-reference traversal yet, and deduplicated inline comments per finding and head SHA. Suggestions replace one added line and require human review.

## Repository-specific review CI

The default review profile requires the aggregate `verify` job from the trusted GitHub Actions app. Boundra supplements that gate with an explicit profile in `apps/worker/src/checks.ts` covering its example, three Node runtimes, four native platform jobs, and benchmark smoke check. Every named job and aggregate `verify` must be present and successful with the GitHub Actions app identity; missing, queued, failed, skipped, or cancelled required checks never permit approval. Both webhook and scheduled review use this profile. Add or update profiles through a reviewed agent PR when a repository changes its CI matrix. Automatic merge still requires the original aggregate `verify`, branch protection, and all other gates; the profile does not enroll Boundra in auto-merge.


## Infrastructure repository opt-in

For oddmash-agents, oddmash-skills and the separately enrolled .github repository, define an organization-owned single-select repository custom property named `oddmash-auto-merge` with allowed values `disabled` and `documentation`. Use a disabled default and leave repository actors unable to edit the property; organization owners can set individual repository values in Settings → Repository → Custom properties → Set values. Do not store this setting in a PR-controlled file. The Reviewer reads the metadata with its existing repository access; no extra write permission or repository enrollment is granted. An absent, duplicate, unknown or unavailable setting fails closed. The `documentation` mode permits only ordinary documentation in the existing protected path policy. Runtime, skill execution, workflow, credential and governance changes are not enabled by the property. The independently reviewed .github enrollment and path policy must also be satisfied. All repositories still require exact-head CI, approval, linked issue evidence, protected base and normal merge commits; the setting is rechecked before authorization.

# Reviewer quality and operations

The reviewer uses a bounded, project-specific focus and may read direct relative imports from the immutable public base commit and complete small changed source files from the reviewed head. Related files are context, not independent finding anchors. Private reviews retain their original changed-patch boundary. Deleted-line findings use LEFT anchors and remain advisory; they cannot carry suggestions or blocking evidence.

Maintainer comment requests that arrive before passing checks persist a bot-authored acknowledgement tied to the exact head. A check-suite completion can resume the request without a second mention. Stale heads and already-recorded requests are ignored. The scan is bounded to 100 comments per type; if exceeded, use the explicit manual command. A failed check requires repair and a passing check event. Native GitHub review requests without a comment still require manual retry if checks are not ready.

Usage events record role, model, phase and numeric input/output/total tokens. See [agent operations](agent-operations.md) for limits, diagnostics and cost estimation.

## Review coverage and merge eligibility

Reviewer quality checks may include conventional configuration manifests, explicitly recognized CI/deployment workflow filenames, and authentication or authorization source under the conventional src directories. These checks are defensive and do not authorize executable security-sensitive suggestions. The private-repository allowlist, changed-patch-only boundary, credential-like content checks, confidential names and rename-origin checks remain enforced. Unrecognized sensitive private paths remain excluded. Standalone source references to environment variables can be reviewed. The private PR report can list ordinary omitted filenames for manual follow-up. Confidential paths and sensitive values remain hidden, and omitted filenames are excluded from model input.

Coverage explanations distinguish confidential paths, private repository policy exclusions, potential sensitive content, missing or incomplete patches, and budget limits. Automatic merge continues to use its independent strict selection and existing low-risk path checks, exact-head approval, issue acceptance, CI and branch protection. Reviewable configuration and authentication changes do not become merge eligible.

## Generated artifacts and configuration

Use the evidence appropriate to the artifact. A frozen-lockfile install proves that the declared dependency graph can be installed consistently; it does not establish dependency safety. Dependency review and applicable audit checks must be evaluated separately. Generated assets and screenshots need deterministic format/build validation or manual visual QA; a green compiler check does not prove visual quality. Conventional configuration can be reviewed defensively, but confidential values and protected paths remain outside model input. Missing lockfile patches, omitted assets and incomplete checks are coverage gaps, not zero findings. CI results do not authorize automatic merge in the presence of missing coverage or protected changes.

## Review outcomes

Confirmed actionable defects request changes. Advisory findings are optional recommendations, not mandatory remediation. After verifying the evidence, the maintainer may accept, defer to a separate issue, or decline with rationale. Do not request another review solely to dispose of optional advice on the same commit. Re-run after a new commit or when evidence needs fresh verification. This policy does not itself grant approval or bypass required review or CI. Incomplete coverage or invalid evidence is listed separately and requires manual verification before approval. The review status label and check title reflect these distinct outcomes. Approval still requires zero findings, complete coverage and passing exact-head checks; merge eligibility is unchanged. Browser lifecycle findings must account for both bfcache preservation and restoration before proposing cleanup.

Anchored findings appear once in their inline threads, including verification steps. The final review body contains the outcome, finding counts and coverage gaps. If inline coverage cannot be confirmed, preserve the full finding text in the review body. Existing same-head inline threads remain deduplicated.

## Evaluation

Maintain a reviewed corpus of synthetic or expressly approved public patches. Include no-defect changes, deleted behavior, incorrect loading states, accessibility regressions, SSR mismatches, intentional alternative implementations, and ordinary correctness regressions. Label expected finding anchors and separately adjudicate whether each finding is genuinely actionable. The anchor evaluator counts true positives, false positives and false negatives without counting duplicate anchors. Anchor matches alone do not prove semantic correctness; evaluate severity, evidence and false blocking manually. Compare model versions on the same corpus before enabling policy changes.

Record maintainer corrections as explicit, reviewed test fixtures or version-controlled product guidance, not as automatically trusted instructions. The bot's discussion verdict does not authorize a review decision. Add cases only after adjudication. See [the first public PR baseline](evaluation-baseline.md) and the reviewed feedback rules in `apps/worker/src/review-feedback.ts`.

## Remaining production rollout

The optional Vercel Queue worker accepts only signed deliveries and persists a bounded target, delivery ID and signature, never credentials or patches. After a reviewed deployment registers the queue trigger, set the repository Actions variable `REVIEWER_QUEUE_ENABLED=true` and redeploy; the default is false. Publish before returning 202. Duplicate delivery IDs are deduplicated; the worker revalidates repository scope and skips stale known heads. Transient failures retry with bounded backoff; quota and permanent failures go to a separate failure topic for maintainer inspection. Failure record publication retries once with the same idempotency key. If both attempts fail, a fixed terminal error is emitted for maintainer alerting without rerunning the paid review; this does not guarantee durable failure storage during a queue outage. Configure monitoring for the exact `Reviewer failure record unavailable after two publish attempts` signal before enabling the worker. Failure records expire after 24 hours. Manual recovery requires a new signed GitHub delivery or an explicit maintainer review request. No scheduled reconciliation is enabled. Verify real webhook deliveries, queue consumption, failure handling, comment permissions, LEFT inline comments and deployment logs before rollout.

The isolated auto-merge module attempts a normal merge immediately after eligible approval, before cosmetic label updates. An acceptance proof is bound to the exact repository, PR, head, base, merge commit and linked issue revision. A redelivery may retry the merge without another model review only if that proof still matches and all current policy gates pass. Approvals predating this proof require a fresh explicit review. Policy exclusions remain unchanged.

When an approved PR cannot be automatically merged, the app posts or refreshes a single bilingual automation-status comment with a safe, actionable reason for the current head. Review request failures use a separate status comment. Repeated identical reasons do not create new comments; after successful processing an existing status is marked completed. Raw exception text, source and credentials are never posted.

# Central webhook deployment

The maintainer may opt all public Oddmash repositories into review by enabling the organization webhook. Internal, archived, external and draft targets are rejected. Five private repositories are explicitly approved by name and immutable ID: oddmash-agents, oddmash-skills, overtime-prototype, cash-out and oddmash-website. New private repositories require separate approval. No contributor code is executed. Existing relay and scheduled review workflows remain unchanged until live webhook verification.

## Deployment

The unlinked Vercel project is `oddmash-reviewer` in team `qtaghdi`. GitHub Actions builds on reviewed main and uploads prebuilt output. Configure a protected GitHub environment named `production` restricted to main and store a scoped Vercel deployment token as environment secret `VERCEL_TOKEN`. No additional GitHub PAT is needed. Run Deploy Reviewer to Vercel manually once, then set the repository variable `VERCEL_DEPLOY_ENABLED=true` for automatic main deployments. No source or secrets are uploaded as CI artifacts.

The main-only deployment job synchronizes the existing GitHub organization secrets `REVIEWER_APP_PRIVATE_KEY` and `OPENAI_API_KEY` to this Vercel project's production environment as sensitive variables, and `REVIEWER_APP_ID` and `REVIEWER_APP_SLUG` from GitHub variables. Add a new strong random repository Actions secret named `REVIEWER_WEBHOOK_SECRET`, then set the same value as the GitHub App webhook secret. The sync enables review only when this secret is configured and `REVIEWER_APP_ENABLED=true` is set in GitHub. Optional `OPENAI_MODEL` defaults to the existing model. The deployment job verifies signed and unsigned ping behavior when a webhook secret exists.

In the Oddmash Reviewer GitHub App, enable the webhook at the project's production HTTPS URL plus `/api/github`, enter the identical webhook secret, and subscribe to Pull request, Check suite, Pull request review comment and Issue comment events. Keep Pull requests write, Checks read and Metadata read. Issue comment subscription requires Issues read access. The same app has Contents write for the separately gated merge module and the existing opt-in verified own-thread resolution exception; ordinary review tokens are still Contents read. See [the agent family permission policy](agent-family.md#separate-github-identities) for the selected-installation boundary and pending live specialist resolution verification. Verify actual installation permissions for label creation. Use a public production domain or explicitly configure protection so GitHub can reach this HMAC-authenticated endpoint; do not expose other deployments.

## Maintainer requests and discussion

- Normal PRs should be opened ready for review; draft PRs are excluded until marked ready. Pending remote CI is not a reason to use draft status. The reviewer still waits for passing current checks before formal review.
- Ready PR events, including head updates, can start a review after final checks. The maintainer can explicitly request another review. The maintainer (`qtaghdi`, verified numeric account ID) can use `/review` in the PR conversation or as an inline reply without mentioning Lead. GitHub's native review request is supported if GitHub permits requesting the app as reviewer.
- Place one standalone slash command on the first non-empty line and optional context on subsequent lines. Use the [agent command table](agent-family.md#slash-commands) for other supported contexts. Legacy App mention commands remain compatible. A bare mention with a question is not a fresh review request. Comments remain limited to 2000 characters; quoted commands, commands embedded in prose, and non-maintainer requests do not initiate reviews.
- For troubleshooting, inspect GitHub App Recent Deliveries and the Vercel runtime log. A valid routed webhook returns `202 Accepted`; an ignored maintainer review request can include a fixed format or length diagnostic in its `200` response. Neither diagnostics nor acknowledgement logs include the comment body, repository name, credentials, or webhook payload. Successful delivery is not evidence that a review has finished.
- The bot adds Eyes on receipt of a comment request and keeps it while processing or waiting for checks. After a completed response, it removes only its own receipt reaction; positive confirmation first adds a thumbs-up, and non-confirming responses leave no thumbs-up. Discussion answers do not modify official review state. Conversation reactions require Issues write, scoped only to the requested repository and comment workflow.
- Automatic review runs once per pull request after required CI. A later head does not trigger a fresh full review automatically. An authorized explicit request starts a fresh evaluation of the current head, even if the app already requested changes. It does not discard an existing change request, approve automatically, or waive CI or merge prerequisites. Replayed requests are ignored after a result is recorded. If checks are not ready, comment requests are recorded against the current head and resumed on a passing check-suite event. Native review requests still require manual retry.
- Reply in the original inline thread. Lead routes a reply without a mention to the verified bot that opened the thread. To request scoped resolution, use `Fixed in <full-current-head-sha>: <specific change and actual verification evidence>`. Explicit mentions remain supported. The bot checks only the original finding and relevant current diff, replies in English, and resolves its own inline thread only when the correction has an exact current-head changed-line evidence match and the thread still belongs to the bot. The comparison runs from the finding’s original commit to the current head, so it can verify a revert even when the corrected file has disappeared from the PR diff. A disputed, stale, unsupported or uncertain correction stays open. A verified correction or supported agreement receives a thumbs-up. If GitHub rejects the reaction or thread resolution, the reply reports which operation failed and a retry for the same thread and revision resumes the existing verified reply. After required CI passes, a full neutral follow-up or explicitly requested approval can check up to six earlier open Lead findings individually. A thread closes only when the exact current-head comparison verifies its correction. Current finding paths and threads with incomplete evidence stay open. Thread reconciliation does not change the official PR review or authorize a merge.
- For a general Conversation finding, mention Lead and use the same scoped fix format with separate `Original: <same-PR comment or review permalink>` and `File: <changed path>` lines. The response is posted in Conversation referencing the original comment. General comments do not have a Resolve action. Do not request repeated whole-PR reviews for ordinary corrections; an explicit maintainer request remains available for a new official review when necessary.
- Only the maintainer's authenticated created-comment events trigger this follow-up workflow. Bot events, edits, unrelated threads and unauthorized private targets are ignored; each thread has a bounded reply budget. No new credentials are required.
- Findings are attached to one pending review and submitted together as one GitHub review, retaining individual inline threads and suggested changes. An existing advisory may be updated when there are no new inline findings. Very large discussions exceeding the bounded pagination budget are withheld and logged for maintainer review rather than publishing potentially duplicate replies.
- A formal change request requires high confidence, medium or high severity, an exact added-line excerpt, a concrete consequence, an applicable requirement, and a separate confirmation pass against the supplied diff. Unconfirmed findings remain advisory, including when confirmation is unavailable or malformed. An advisory is not an approval and does not permit auto-merge; passing checks and complete coverage remain required for approval.
- Manual review reports identify the reason, affected file or line when safe, and the concrete verification action in English. Files without text diffs (including image assets), truncated diffs, policy exclusions, and review limits are distinguished. A bounded list of safe paths is shown in the PR, including ordinary omitted filenames in an enrolled private repository. Confidential names and sensitive content remain undisclosed. Coverage diagnostics are generated locally, not sent to the model, and do not relax the approval or merge gates.

## GitHub authorization quota handling

The worker records classified authorization operations separately as `app-identity`, `installation-identity`, `installation-token-mint`, `installation-token-revoke`, and `repository-identity`. Logs contain only bounded categories, status and numeric quota metadata, never an authorization header, token, raw API path, or application/installation identity.

An authenticated authorization GET that returns HTTP 403 or 429 with zero remaining primary quota and a credible future reset records a temporary cooldown. The process-local cache separates the configured signed App JWT identity from its minted installation identity; it retains at most 32 entries and accepts a reset no more than 3605 seconds ahead. A subsequent authorization read for that exact quota scope fails closed until reset. When an installation quota is already known exhausted, authorization stops before another token mint. This is negative evidence only: no cached installation or repository authorization success is substituted, and a fresh identity check is required after expiry. Existing check evidence, permissions, ordinary request handling and write retry policy remain unchanged.

The `github_request_deferred` event and `quota-deferred` metric outcome indicate a local deferral, not a network request or a new GitHub response. The cooldown stores no credentials; its numeric scope keys remain in memory and are never emitted. The mechanism covers only a warm worker process; different regions, cold starts and parallel in-flight requests may still independently observe the limit. It does not schedule another execution or change queue retry policy. Stop repeated operator requests until the recorded quota reset, then request a fresh review against the current head. Never bypass GitHub quotas or required CI to recover a review.

## Verification and migration

Optional review progress: after maintainer approval of the GitHub App Checks read/write permission, set `REVIEWER_CHECK_PROGRESS_ENABLED=true` on the webhook runtime. Eligible ready PRs display `Waiting for CI` while checks are pending, then reuse that same head- and request-scoped check for Lead review, the active specialist, and verification of earlier findings. Failed required CI ends the check with a neutral blocked result; a successful CI rerun can start a new check. The progress check is informational and must not be configured as a required branch check. The configured reviewer App identity and exact check name distinguish it from CI evidence. Failed progress requests do not replace the review or its approval requirements. Keep the setting disabled until the permission change has been reviewed. The scheduled fallback remains read-only for Checks; subsequent webhook reconciliation can complete an existing progress check from an already submitted exact-head review.

Check a signature-authenticated ping delivery, an ordinary public PR, a fork PR and completed checks. Verify review decisions, labels, and no review for unapproved private repositories. Verify approved private PRs use authenticated check reads, omit sensitive files and enter the merge policy only for eligible low-risk changes. Wait for the completed aggregate verify check and update an existing same-head advisory review in place. The pending-review lock serializes competing webhook and fallback deliveries; clean CI-pending events do not post a review. Background processing is bounded, not a durable general-purpose queue; comment requests waiting for CI can resume, but other failures require redelivery or a maintainer manual review. Do not disable old workflows until live verification and a deduplication strategy are in place.

## Maintainer-only auto-merge pilot

The separately gated merge policy covers all five public product repositories and the five explicitly approved private repository identities. The exact public Oddmash/.github identity permits maintainer PRs targeting main that modify only its allowlisted ordinary Markdown guidance, profile and localized contributor docs, and existing Markdown issue/PR templates. Workflows, configuration, CODEOWNERS, security and AI review policy, and other paths remain manual. Set the repository Actions variable `REVIEWER_AUTO_MERGE_ENABLED=false` and redeploy to stop it. Unapproved repositories, fork PRs and external contributors are excluded. Private agent and skill repositories permit only ordinary root README documentation; runtime, skill and governance changes remain manual. For the website, the authored static JavaScript and CSS in dist/ are eligible; game source roots are not yet approved and only ordinary documentation is eligible. Only `qtaghdi` (verified numeric account ID) PRs into protected main with a single standalone same-repository `Refs #N`, `Closes #N`, `Fixes #N` or `Resolves #N` line and a maintainer-authored open issue containing explicit acceptance criteria are eligible. `Refs` is non-closing and requires verified PR scope from its acceptance checklist or Summary; closing references require full issue completion evidence. Boundra allows ordinary supported source files under packages/runtime/src/ and packages/ui/src/ and additive tests under their tests/ roots; Rust core changes remain manual. Eligible changes include ordinary Markdown and allowlisted product source paths, plus additive tests that do not remove assertions or disable tests. Configuration, generated code, permissions, release, architecture, security, data and non-allowlisted organizational policy changes remain manual. Missing evidence leaves the PR open. GitHub Actions verify must be required on the protected branch, all required repository-specific current checks must pass, and exact-head independent app approval and validated acceptance evidence must exist. The merge module mints a repository-scoped Contents write token only after the checks and uses a head-SHA-guarded normal merge commit, without bypassing rules. Review-only behavior is unchanged for all ineligible PRs.

## Private review data boundary

Only the five explicitly approved private repository identities are eligible. Review uses a repository-scoped Contents read, Pull requests write and Checks read token. Eligible changed patches and bounded selected guidance are sent to the configured OpenAI API with `store: false`; approved private repositories can be eligible only under the same deterministic merge gates and stricter data filtering, including issue acceptance text. Credential-like values, sensitive configuration and workflow paths, deployment and auth-related files, data dumps and renamed sensitive paths are excluded; omitted filenames are not sent. The filter is conservative and is not a guarantee against all sensitive content. Incomplete coverage requires maintainer review. Do not add secrets to source or guidance.

## Owner model settings

The console's Agent models card stages one optional override for each existing role. Save applies the choice to subsequent authenticated webhook and queue jobs only, including coordinated specialists. It does not change GitHub App identities, API keys, repo eligibility, review authority, token/request limits, auto-merge, queue settings, or manually dispatched CLI and Actions models. The settings overview's worker model snapshot remains deployment configuration; the Agent models card shows the choices saved for future jobs.

Alternates are opt-in per role. Configure the following plain-text Vercel production variables with a comma-separated list of model IDs approved for that role and compatible with its existing Responses API and structured-output contract:

- `REVIEWER_OPERATOR_ALLOWED_MODELS` for Lead.
- `IMPACT_OPERATOR_ALLOWED_MODELS`, `TRIAGE_OPERATOR_ALLOWED_MODELS`, `QA_OPERATOR_ALLOWED_MODELS`, `RELEASE_OPERATOR_ALLOWED_MODELS`, `DOCS_OPERATOR_ALLOWED_MODELS`, and `ARCHITECT_OPERATOR_ALLOWED_MODELS` for the matching specialists.

Before approving a model, verify availability with the existing role's OpenAI project, structured output and cost limits. No model is implicitly approved from another role's configuration. The console shows the actual deployment default (role-specific `<ROLE>_OPENAI_MODEL` or shared `OPENAI_MODEL`) even when no alternates are configured. The operator can inherit the default without saving its model ID. A revoked model is no longer effective; the worker falls back to the deployment default and the next save must remove or replace revoked choices. Unavailable model settings also fall back to the deployment model. There is no automatic retry with another model on a provider failure, preserving existing request budgets.

Direct webhook delivery and queue delivery both call the same worker execution entry, which reads the model record once and passes choices through dedicated and coordinated advisor configuration. The offline worker fixtures check the selected provider model for both specialist paths without network access.

Model settings use the existing authenticated owner API boundary, exact revision comparison and a separate bounded 50-entry audit list. They are stored separately from participation and budget controls, so older releases ignore them. Remove alternates from deployment configuration to revoke console selection. Roll back to an earlier reviewed release if needed; its worker will use deployment configuration. Never put credentials or arbitrary identifiers in approved model lists.

The internal console API, `GET /api/models` and `POST /api/models`, requires an authorized owner session and returns private, uncached data. The GET response includes the current revision (null before the first save), role overrides, last update and server-side model policy. The console submits only `revision` and `overrides` to POST using its same-origin JSON request. An absent role inherits its deployment model. The server rejects disallowed selections or malformed records with 400, unauthenticated access with 401, invalid write origin or content type with 403, revision conflicts with 409, and unavailable storage with 503. A 409 response contains no replacement revision; reload the saved values, review them, acknowledge Use my draft, and explicitly Save again, or discard and adopt the latest settings. Operators should use the console rather than constructing API requests manually.

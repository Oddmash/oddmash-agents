# Central webhook deployment

The maintainer may opt all public Oddmash repositories into review by enabling the organization webhook. Internal, archived, external and draft targets are rejected. Five private repositories are explicitly approved by name and immutable ID: oddmash-agents, oddmash-skills, overtime-prototype, cash-out and oddmash-website. New private repositories require separate approval. No contributor code is executed. Existing relay and scheduled review workflows remain unchanged until live webhook verification.

## Deployment

The unlinked Vercel project is `oddmash-reviewer` in team `qtaghdi`. GitHub Actions builds on reviewed main and uploads prebuilt output. Configure a protected GitHub environment named `production` restricted to main and store a scoped Vercel deployment token as environment secret `VERCEL_TOKEN`. No additional GitHub PAT is needed. Run Deploy Reviewer to Vercel manually once, then set the repository variable `VERCEL_DEPLOY_ENABLED=true` for automatic main deployments. No source or secrets are uploaded as CI artifacts.

The main-only deployment job synchronizes the existing GitHub organization secrets `REVIEWER_APP_PRIVATE_KEY` and `OPENAI_API_KEY` to this Vercel project's production environment as sensitive variables, and `REVIEWER_APP_ID` and `REVIEWER_APP_SLUG` from GitHub variables. Add a new strong random repository Actions secret named `REVIEWER_WEBHOOK_SECRET`, then set the same value as the GitHub App webhook secret. The sync enables review only when this secret is configured and `REVIEWER_APP_ENABLED=true` is set in GitHub. Optional `OPENAI_MODEL` defaults to the existing model. The deployment job verifies signed and unsigned ping behavior when a webhook secret exists.

In the Oddmash Reviewer GitHub App, enable the webhook at the project's production HTTPS URL plus `/api/github`, enter the identical webhook secret, and subscribe to Pull request, Check suite, Pull request review comment and Issue comment events. Keep Pull requests write, Checks read and Metadata read. Issue comment subscription requires Issues read access. The same app has Contents write for the separately gated merge module; review tokens are still Contents read. Verify actual installation permissions for label creation. Use a public production domain or explicitly configure protection so GitHub can reach this HMAC-authenticated endpoint; do not expose other deployments.

## Maintainer requests and discussion

- Normal PRs should be opened ready for review; draft PRs are excluded until marked ready. Pending remote CI is not a reason to use draft status. The reviewer still waits for passing current checks before formal review.
- Automatic review runs once per PR, after final checks. Later commits require a deliberate maintainer request. The maintainer (`qtaghdi`, verified numeric account ID) can use `@oddmash-reviewer`, `@oddmash-reviewer /review` or `@oddmash-reviewer /rereview` in the PR conversation or an inline reply. GitHub's native review request is supported if GitHub permits requesting the app as reviewer.
- To attach verification context, place the explicit `/review` or `/rereview` command on the first non-empty line and the explanation on subsequent lines. The existing standalone commands also work. A bare mention with a question is not a fresh review request. Comments remain limited to 2000 characters; quoted commands, commands embedded in prose, and non-maintainer requests do not initiate reviews.
- For troubleshooting, inspect GitHub App Recent Deliveries and the Vercel runtime log. A valid routed webhook returns `202 Accepted`; an ignored maintainer review request can include a fixed format or length diagnostic in its `200` response. Neither diagnostics nor acknowledgement logs include the comment body, repository name, credentials, or webhook payload. Successful delivery is not evidence that a review has finished.
- The bot adds Eyes on receipt of a comment request, replies when checks are not ready, and adds a thumbs-up after successful approval or when a substantive discussion argument is supported. Discussion answers do not modify review state. Conversation reactions require Issues write, scoped only to the requested repository and comment workflow.
- A request starts a fresh evaluation of the current head, even if the app already requested changes. It does not discard an existing change request, approve automatically, or waive CI or merge prerequisites. Replayed requests are ignored after a result is recorded. If checks are not ready, comment requests are recorded against the current head and resumed on a passing check-suite event. Native review requests still require manual retry.
- Reply to an existing Reviewer inline finding with `@oddmash-reviewer` and a question or rationale. The bot reads the bounded, filtered thread and relevant current diff, then replies in English with Korean in a collapsed section. It may acknowledge an unsupported finding. A discussion reply never changes review state; request a fresh review separately.
- Only the maintainer's authenticated created-comment events trigger this follow-up workflow. Bot events, edits, unrelated threads and unauthorized private targets are ignored; each thread has a bounded reply budget. No new credentials are required.
- Findings are attached to one pending review and submitted together as one GitHub review, retaining individual inline threads and suggested changes. An existing advisory may be updated when there are no new inline findings. Very large discussions exceeding the bounded pagination budget are withheld and logged for maintainer review rather than publishing potentially duplicate replies.
- A formal change request requires high confidence, medium or high severity, an exact added-line excerpt, a concrete consequence, an applicable requirement, and a separate confirmation pass against the supplied diff. Unconfirmed findings remain advisory, including when confirmation is unavailable or malformed. An advisory is not an approval and does not permit auto-merge; passing checks and complete coverage remain required for approval.
- Manual review reports identify the reason, affected file or line when safe, and the concrete verification action in English and Korean. Files without text diffs (including image assets), truncated diffs, policy exclusions, and review limits are distinguished. A bounded list of safe public paths is shown; private and sensitive omitted paths and content remain undisclosed. Coverage diagnostics are generated locally, not sent to the model, and do not relax the approval or merge gates.

## Verification and migration

Check a signature-authenticated ping delivery, an ordinary public PR, a fork PR and completed checks. Verify review decisions, labels, and no review for unapproved private repositories. Verify approved private PRs use authenticated check reads, omit sensitive files and enter the merge policy only for eligible low-risk changes. Wait for the completed aggregate verify check and update an existing same-head advisory review in place. The pending-review lock serializes competing webhook and fallback deliveries; clean CI-pending events do not post a review. Background processing is bounded, not a durable general-purpose queue; comment requests waiting for CI can resume, but other failures require redelivery or a maintainer manual review. Do not disable old workflows until live verification and a deduplication strategy are in place.

## Maintainer-only auto-merge pilot

The separately gated merge policy covers the existing four public product repositories and the five explicitly approved private repository identities. Set the repository Actions variable `REVIEWER_AUTO_MERGE_ENABLED=false` and redeploy to stop it. Unapproved repositories, organization policy, fork PRs and external contributors are excluded. Private agent and skill repositories permit only ordinary root README documentation; runtime, skill and governance changes remain manual. For the website, the authored static JavaScript and CSS in dist/ are eligible; game source roots are not yet approved and only ordinary documentation is eligible. Only `qtaghdi` (verified numeric account ID) PRs into protected main with a single standalone `Closes #N`, `Fixes #N` or `Resolves #N` line and a maintainer-authored open issue containing explicit acceptance criteria are eligible. Eligible changes include ordinary Markdown and allowlisted product source paths, plus additive tests that do not remove assertions or disable tests. Configuration, generated code, permissions, release, architecture, security, data and organizational policy changes remain manual. Missing evidence leaves the PR open. GitHub Actions verify must be required on the protected branch, current checks must pass, and exact-head independent app approval and validated acceptance evidence must exist. The merge module mints a repository-scoped Contents write token only after the checks and uses a head-SHA-guarded normal merge commit, without bypassing rules. Review-only behavior is unchanged for all ineligible PRs.

## Private review data boundary

Only the five explicitly approved private repository identities are eligible. Review uses a repository-scoped Contents read, Pull requests write and Checks read token. Eligible changed patches and bounded selected guidance are sent to the configured OpenAI API with `store: false`; approved private repositories can be eligible only under the same deterministic merge gates and stricter data filtering, including issue acceptance text. Credential-like values, sensitive configuration and workflow paths, deployment and auth-related files, data dumps and renamed sensitive paths are excluded; omitted filenames are not sent. The filter is conservative and is not a guarantee against all sensitive content. Incomplete coverage requires maintainer review. Do not add secrets to source or guidance.
